# PAI iOS

Native SwiftUI client for PAI Cloud — a personal system that runs Claude Code sessions on a cloud
VM and drives them from a phone. This app is the iPhone front end for it.

**This is not an app you can install and use.** It talks to one specific privately-hosted backend,
and that backend is not public. It is here because the parts underneath it are worth reading and
reusing, and because a public repository gets unmetered CI.

## What is worth taking from here

| | Where |
|---|---|
| A chat transcript that never jumps while loading older messages — `UICollectionView`, precomputed heights, prepend compensation in the layout rather than after a batch update | `PAIKit/Sources/PAIKit/Layout/`, `PAI/Transcript/` |
| A markdown editor over one plain `UITextView`, with syntax highlighting over the source rather than a live preview | `PAIKit/Sources/PAIKit/Editor/`, `PAI/Notes/Editor/` |
| Notes that work in flight mode: a cached index and notes, files kept under a size budget, and an outbox that holds every unsaved edit until the server has it, with conflicts settled without asking and nothing lost | `PAIKit/Sources/PAIKit/Stores/Notes/` |
| A markdown parser that decomposes into synchronously measurable blocks, on top of swift-markdown, with LaTeX typeset natively by SwiftMath so a formula's size is known before layout | `PAIKit/Sources/PAIKit/Markdown/`, `PAIKit/Sources/PAIKit/Layout/MathTypesetter.swift` |
| A debug bridge — an HTTP server inside the app, `#if DEBUG`, so CI can ask the app what it thinks instead of reading pixels off a screenshot | `PAIKit/Sources/PAIKit/Debug/` |
| Streaming over `URLSessionDataDelegate` rather than `URLSession.bytes(for:)`, so the transport compiles and tests on Linux | `PAIKit/Sources/PAIKit/Networking/` |
| Building and shipping an iOS app **without owning a Mac** — signing from Linux via the App Store Connect API, a hand-written project file, TestFlight from CI | `.github/workflows/`, `fastlane/`, `Tooling/` |

That last one is the least documented thing on the internet and the most annoying to work out, so
it is the part most likely to be useful to someone else.

## How it is arranged, and why

Almost everything lives in `PAIKit`, a local Swift package. **The package builds and tests on
Linux; the app target compiles only on macOS.** That split is the whole architecture: package code
is proven in seconds for free, app-target code is proven only when a macOS runner runs. So the
views are thin, and anything a unit test could catch lives in the package.

| Path | What |
|---|---|
| `PAIKit/` | the logic and its tests — where the code is |
| `PAI/` | app target: views, and the few things needing an Apple framework. A buildable folder, so new files need no project edit |
| `PAI.xcodeproj` | written by hand, small, not regenerated by any tool |
| `Config/` | xcconfig; `MARKETING_VERSION` comes from the git tag via CI |
| `Tooling/` | checks that catch macOS-only compile errors without a Mac; `sim/` is the simulator lane the `Mac` workflow runs, usable on any Mac |
| `fastlane/` | build, sign, upload — the same lanes locally and in CI |

## Signing in

The backend sits behind Zitadel. "Sign in" runs the authorization-code flow with PKCE in the system
browser sheet (`WebAuthenticationSession`, the shared browser session, so a login already made in
Safari is reused) against a native, public Zitadel application, and comes back through
`pai://oauth/callback`. The token set lands in the Keychain. When the backend refuses the access
token — a 401, or the proxy's plain-text 403 — the app refreshes it once, however many requests were
refused together, sends the request again, and signs out only when the refresh itself is refused.
`PAIKit/Sources/PAIKit/Auth/` holds the flow, the token endpoint and the renewal; the Keychain store
and the screen are in `PAI/Shell/`.

Signing in is the only way in: the app has no field for a pasted token, and a phone that still
holds one from an earlier version is asked to sign in. Every request carries the phone's name in
`X-Device-Name` (iOS reports the generic model name, such as "iPhone", unless the device name
entitlement is granted), so the backend's list of signed-in devices can show it. Signing out
revokes the refresh token at Zitadel as well as clearing the phone, and a backend that revokes the
device from that list signs the app out the next time it asks (`401` with `device_revoked`), with
the message "This device was signed out".

## The share extension

`PAIShare/` is a second target: PAI in the system share sheet. A shared photo, PDF, text file, selected text or link goes through the same `POST /api/drafts/{key}/attachments` a composer's upload uses, onto an existing session's draft or the new-session draft, and waits there until a message is sent from it. The view holds only what needs an Apple framework; `ShareStore` in `PAIKit` holds the rest. The app copies its sign-in into a Keychain item in a shared access group, which the team wildcard in every provisioning profile already covers, so neither bundle id needs a capability or an App Group.

Signing needs one thing the app alone does not: the App Store profile `PAI Share App Store` for `com.frederikberg.pai.share`, in the repository secret `IOS_SHARE_PROVISIONING_PROFILE_BASE64`.

## The Control Center control

`PAIControls/` is a third target, a WidgetKit extension offering one 1x1 control, Quick actions, that opens the quick-actions screen from Control Center, the Lock Screen or the Action button. `SharedIntents/` holds the intent it runs and is compiled into the app as well as the extension: a control opens the app only when the app holds the very same intent type.

Signing needs the App Store profile `PAI Controls App Store` for `com.frederikberg.pai.controls`, in the repository secret `IOS_CONTROLS_PROVISIONING_PROFILE_BASE64`.

## Notes offline

The notes open without a connection. The index, every note opened on the phone, the favourites,
each container's attachment list and every file viewed are kept on disk, so the list, the filter,
the "Find note" quick action and those notes and files work in flight mode. A note never opened
says it is not on the phone.

Editing the body, renaming and favouriting work offline. Every unsaved edit is written to disk
within a moment of typing and again before each save leaves, and stays there until the server has
it, so neither flight mode nor the app being killed loses one. Edits that waited go out when the
network is back, bodies before renames. If the note changed on the server meanwhile, the phone's
version is written over it and the version it replaced stays in the note's history; a toast says
so. An edit typed while online that the app could not save before it was killed is sent as an
ordinary save instead, so a change made elsewhere in between raises the conflict banner. Creating
and deleting notes, adding or changing files, full-text and semantic search, history, links, the
summary and sharing need a connection and say so.

Every save from the phone is recorded in the note's history as the phone's (`phone`, or `offline`
for an edit that waited), never as the web's, so a phone save and a burst of web saves each keep the
version they replace. A rename made on the web while the phone was offline still loses to a waiting
phone edit of a note linking to it: the link rewrite is in the history, the phone's text is what
stays.

An edit the server refuses (most often because the note was deleted elsewhere) is not sent again by
itself. The save badge in the editor and Settings → Notes offline offer to copy or discard its
text; the same list holds any saved edit a different version of the app wrote in a form this one
cannot read, which is set aside rather than overwritten.

Settings → Notes offline sets how much space this takes (5 GB by default), shows what is used,
and clears it. Only files are dropped to stay under the size, oldest first. Clearing never touches
edits that have not synced, and keeps those notes on the list.

## Building and checks

The package needs only a Swift 6.2 toolchain, on any platform:

```
swift build --package-path PAIKit --build-tests && \
  swift test --package-path PAIKit --skip-build
swift format lint --recursive --strict PAIKit PAI PAIShare PAIControls SharedIntents
```

Two scans cover the app target without an iOS SDK: `./Tooling/parse-swift.sh` checks syntax (it stops
before name resolution), and `./Tooling/swift6-lint.py` flags the few Swift 6 constructs that compile
on Linux and fail on a Mac.

The app target needs Xcode. CI builds it on a macOS runner; there is no way around that, and no
attempt here to pretend otherwise.

## CI

Checks run on pull requests only; `main` runs nothing, and the `Validation` job of `Free checks` is
the required gate.

| Workflow | Answers | Runner | Runs on |
|---|---|---|---|
| `Free checks` | compiles, tests pass, formatted | Linux | pull requests, manual dispatch |
| `Mac` | the app target compiles and the built bundle declares what it needs; on dispatch it also boots the app, screenshots it and queries the debug bridge | macOS | pull requests that change the app, package, project or config (through `Free checks`), manual dispatch |
| `Release` | signs and ships to TestFlight | macOS | a `v*.*.*` tag, manual dispatch |

A dispatch can ask one question: `gh workflow run mac.yml -f only=note,notes-offline` runs those
screens or sections of `Tooling/sim/sweep.sh`, and `-f script=<path>` sources a probe from the branch
after them. Either also skips the macOS-only tests.

`Mac` publishes the screenshots and the device log as artifacts, because every automated assertion
in that job can pass while the screen renders nothing.

## Releasing

Push a `v*.*.*` tag, or dispatch the workflow. The tag is the single source of truth for the
version; the build number is the CI run number. TestFlight builds expire after 90 days;
dispatching with `refresh_tag` rebuilds an existing release under a new build number to keep an
installed copy launching.
