# PAI iOS

Native SwiftUI client for PAI Cloud — a personal system that runs Claude Code sessions on a cloud
VM and drives them from a phone. This app is the iPhone front end for it.

**This is not an app you can install and use.** It talks to one specific privately-hosted backend,
and that backend is not public. It is here because the parts underneath it are worth reading and
reusing, and because a public repository gets unmetered CI.

## What is worth taking from here

| | Where |
|---|---|
| A chat transcript that never jumps while loading older messages — `UICollectionView`, precomputed heights, prepend compensation in the layout rather than after a batch update | `PAIKit/Sources/PAIKit/Layout/`, `PAI/Transcript/` |
| A markdown editor over one plain `UITextView`, with syntax highlighting over the source rather than a live preview | `PAIKit/Sources/PAIKit/Editor/`, `PAI/Notes/Editor/` |
| A markdown parser that decomposes into synchronously measurable blocks, on top of swift-markdown | `PAIKit/Sources/PAIKit/Markdown/` |
| A debug bridge — an HTTP server inside the app, `#if DEBUG`, so CI can ask the app what it thinks instead of reading pixels off a screenshot | `PAIKit/Sources/PAIKit/Debug/` |
| Streaming over `URLSessionDataDelegate` rather than `URLSession.bytes(for:)`, so the transport compiles and tests on Linux | `PAIKit/Sources/PAIKit/Networking/` |
| Building and shipping an iOS app **without owning a Mac** — signing from Linux via the App Store Connect API, a hand-written project file, TestFlight from CI | `.github/workflows/`, `fastlane/`, `Tooling/` |

That last one is the least documented thing on the internet and the most annoying to work out, so
it is the part most likely to be useful to someone else.

## How it is arranged, and why

Almost everything lives in `PAIKit`, a local Swift package. **The package builds and tests on
Linux; the app target compiles only on macOS.** That split is the whole architecture: package code
is proven in seconds for free, app-target code is proven only when a macOS runner runs. So the
views are thin, and anything a unit test could catch lives in the package.

| Path | What |
|---|---|
| `PAIKit/` | the logic and its tests — where the code is |
| `PAI/` | app target: views, and the few things needing an Apple framework. A buildable folder, so new files need no project edit |
| `PAI.xcodeproj` | written by hand, small, not regenerated by any tool |
| `Config/` | xcconfig; `MARKETING_VERSION` comes from the git tag via CI |
| `Tooling/` | checks that catch macOS-only compile errors without a Mac |
| `fastlane/` | build, sign, upload — the same lanes locally and in CI |

## Building

The package needs only a Swift 6.2 toolchain, on any platform:

```
swift build --package-path PAIKit --build-tests
swift test  --package-path PAIKit --skip-build
```

The app target needs Xcode. CI builds it on a macOS runner; there is no way around that, and no
attempt here to pretend otherwise.

## CI

| Workflow | Answers | Runner |
|---|---|---|
| `Free checks` | compiles, tests pass, formatted | Linux |
| `Mac` | does it actually run — boots it, screenshots it, queries the debug bridge | macOS |
| `Release` | signs and ships to TestFlight | macOS |

`Mac` publishes the screenshot and the device log as artifacts, because every automated assertion
in that job can pass while the screen renders nothing.

## Releasing

Push a `v*.*.*` tag, or dispatch the workflow. The tag is the single source of truth for the
version; the build number is the CI run number. TestFlight builds expire after 90 days.
